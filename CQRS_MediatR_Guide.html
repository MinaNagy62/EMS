CQRS & MediatR

A complete guide from zero to hero — with examples from your EMS project

1. The Problem We're Solving

The Fat Service Problem

As applications grow, service classes become monsters. They handle reads, writes, validation, caching, logging — everything. This is called the "Fat Service" or "God Class" anti-pattern.

Your Real Code — DepartmentService

Look at your current DepartmentService. It already has 4 injected dependencies and 5 methods:

public class DepartmentService : IDepartmentService
{
    // ALL dependencies injected — even if a method only needs 1-2 of them
    private readonly IUnitOfWork _unitOfWork;
    private readonly IValidator<CreateDepartmentRequest> _createValidator;
    private readonly IValidator<UpdateDepartmentRequest> _updateValidator;
    private readonly IMemoryCache _cache;

    // READS — only need _unitOfWork and _cache
    public async Task<PagedResponse<DepartmentResponse>> GetAllDepartmentsAsync(...) { ... }
    public async Task<DepartmentResponse> GetDepartmentByIdAsync(...) { ... }

    // WRITES — only need _unitOfWork and _createValidator or _updateValidator
    public async Task<DepartmentResponse> CreateDepartmentAsync(...) { ... }
    public async Task<DepartmentResponse> UpdateDepartmentAsync(...) { ... }
    public async Task DeleteDepartmentAsync(...) { ... }
}

What's wrong with this?

GetAllDepartmentsAsync doesn't need _createValidator or _updateValidator — but they're still injected and constructed.

DeleteDepartmentAsync doesn't need _cache or any validator — but they're still there.

Every method pays the cost of every dependency, even the ones it doesn't use.

Now imagine adding more features: GetByCode, GetActiveCount, BulkImport, MergeDepartments, TransferEmployees... The class grows to 15+ methods with 10+ dependencies. This doesn't scale.

2. CQRS — Command Query Responsibility Segregation

What Is CQRS?

CQRS is a pattern that says: split your reads and writes into separate models.

Instead of one service class handling everything, each operation becomes its own pair of classes:

Before One Service

Controller
    ↓
DepartmentService
    ↓
Repository

One class does everything. 5 methods, 4 dependencies.

After CQRS

Controller
    ↓
Command or Query
    ↓
Handler
    ↓
Repository

Each operation is its own class. 1 method, 1-2 dependencies.

Commands vs Queries

Command Query
Purpose Change state (write) Read state (read)
Examples Create, Update, Delete GetAll, GetById, Search
Returns The created/updated object (or nothing) Data (DTOs, lists, counts)
Side effects Yes — changes the database No — only reads
Idempotent? Usually no (creating twice = 2 records) Yes (reading twice = same result)
Needs validation? Yes (validate input before changing state) Rarely (maybe validate page number)

Why It's Better

Benefit Explanation
Single Responsibility Each handler does exactly one thing. CreateDepartmentHandler only creates.
Minimal dependencies Each handler injects only what it needs. No wasted resources.
Easy to test Mock 2 dependencies instead of 10. Tests are focused and small.
Open/Closed Principle Adding a feature = adding a new file. You never modify existing handlers.
Separate optimization Reads can use caching, projections, read replicas. Writes can use transactions, validation. They don't interfere.
Less merge conflicts Developers work on different files, not the same 500-line service.

3. MediatR — The Dispatcher

What Is MediatR?

With CQRS, we have Commands, Queries, and Handlers — but how does the controller know which handler to call? That's what MediatR does. It's a simple in-process message dispatcher.

Controller: "Hey MediatR, handle this GetAllDepartmentsQuery" MediatR: "Let me check the DI container... found GetAllDepartmentsHandler!" MediatR: → calls handler.Handle(query) Handler: → queries database, maps DTOs, returns result MediatR: → returns result to controller

How does MediatR find the right handler?

MediatR scans the assembly at startup (just like FluentValidation scans for validators). It registers every class that implements IRequestHandler<TRequest, TResponse>. When you send a GetAllDepartmentsQuery, MediatR looks up which handler is registered for that type and calls it.

IRequest<T> — "What I Want"

Every command and query implements IRequest<T> where T is the return type:

// QUERY: "I want a paged list of departments"
public class GetAllDepartmentsQuery : IRequest<PagedResponse<DepartmentResponse>>
{
    public int PageNumber { get; set; } = 1;
    public int PageSize { get; set; } = 10;
    public string? Search { get; set; }
}

// COMMAND: "Create this department and give me the result"
public class CreateDepartmentCommand : IRequest<DepartmentResponse>
{
    public string Name { get; set; }
    public string Code { get; set; }
    public string? Description { get; set; }
}

Notice the pattern

The query carries filter/pagination params. The command carries the data to create/update. They're just DTOs with IRequest<T> added. In your current code, these are DepartmentQueryRequest and CreateDepartmentRequest — they'll become the commands and queries themselves.

IRequestHandler<TRequest, TResponse> — "How I Do It"

Each handler implements IRequestHandler<TRequest, TResponse> and has a single Handle method:

public class GetAllDepartmentsHandler
    : IRequestHandler<GetAllDepartmentsQuery, PagedResponse<DepartmentResponse>>
{
    private readonly IUnitOfWork _unitOfWork;
    private readonly IMemoryCache _cache;
    // ↑ Only injects what THIS handler needs — no validators needed for a read!

    public GetAllDepartmentsHandler(IUnitOfWork unitOfWork, IMemoryCache cache)
    {
        _unitOfWork = unitOfWork;
        _cache = cache;
    }

    public async Task<PagedResponse<DepartmentResponse>> Handle(
        GetAllDepartmentsQuery request,
        CancellationToken cancellationToken)
    {
        // Your existing GetAllDepartmentsAsync logic goes here
        // Check cache → build filters → query DB → map to DTOs → return
    }
}
public class CreateDepartmentHandler
    : IRequestHandler<CreateDepartmentCommand, DepartmentResponse>
{
    private readonly IUnitOfWork _unitOfWork;
    // ↑ No validator needed here — ValidationBehavior handles it automatically!
    // ↑ No cache needed here — but we DO need to invalidate (see below)

    public CreateDepartmentHandler(IUnitOfWork unitOfWork)
    {
        _unitOfWork = unitOfWork;
    }

    public async Task<DepartmentResponse> Handle(
        CreateDepartmentCommand request,
        CancellationToken cancellationToken)
    {
        // Map command → entity, save, map back → response DTO
        var department = request.ToEntity();
        department.CreatedAt = DateTime.UtcNow;

        await _unitOfWork.Departments.AddAsync(department);
        await _unitOfWork.SaveChangesAsync();

        return department.ToResponse();
    }
}

IMediator in the Controller

The controller no longer injects the service. It injects IMediator and sends requests:

[ApiController]
[Route("api/[controller]")]
[Authorize]
public class DepartmentController : ControllerBase
{
    private readonly IMediator _mediator;
    // ↑ ONE dependency. That's it. Forever.

    public DepartmentController(IMediator mediator)
    {
        _mediator = mediator;
    }

    [HttpGet]
    public async Task<IActionResult> GetAll([FromQuery] GetAllDepartmentsQuery query)
    {
        var result = await _mediator.Send(query);
        return Ok(ApiResponse<PagedResponse<DepartmentResponse>>.SuccessResponse(result));
    }

    [HttpPost]
    [Authorize(Roles = "Admin")]
    public async Task<IActionResult> Create([FromBody] CreateDepartmentCommand command)
    {
        var result = await _mediator.Send(command);
        return CreatedAtAction(nameof(GetById), new { id = result.Id },
            ApiResponse<DepartmentResponse>.SuccessResponse(result, "Department created."));
    }
}

The controller is now even thinner

It doesn't know about services, validators, caches, or repositories. It only knows MediatR. Adding a new endpoint = one new _mediator.Send() call + a new Command/Query + Handler in a separate file. The controller barely changes.

Full Request Flow

Let's trace a complete request from HTTP to database and back:

1. Client sends POST /api/department with body { "name": "HR", "code": "HR01" } 2. ASP.NET routing → DepartmentController.Create() Model binding creates CreateDepartmentCommand from JSON body 3. Controller calls _mediator.Send(command) Controller's job is done — it just sends and wraps the response 4. MediatR checks DI: "Who handles CreateDepartmentCommand?" → Finds CreateDepartmentHandler 5. MediatR runs Pipeline Behaviors (if any): → LoggingBehavior logs "Handling CreateDepartmentCommand" → ValidationBehavior finds CreateDepartmentValidator, validates If invalid → throws ValidationException → middleware returns 422 6. MediatR calls handler.Handle(command, cancellationToken) 7. Handler: → Maps command to Department entity → Sets CreatedAt → Calls _unitOfWork.Departments.AddAsync() → Calls _unitOfWork.SaveChangesAsync() ← actual SQL INSERT → Maps entity back to DepartmentResponse → Returns DepartmentResponse 8. LoggingBehavior logs "Handled CreateDepartmentCommand in 42ms" 9. MediatR returns result to controller 10. Controller wraps in ApiResponse<T>.SuccessResponse() → Returns 201 Created with Location header

Install MediatR

dotnet add package MediatR
dotnet add package MediatR.Extensions.Microsoft.DependencyInjection

Then register in DependencyInjection.cs:

public static IServiceCollection AddApplication(this IServiceCollection services)
{
    services.AddMediatR(cfg =>
        cfg.RegisterServicesFromAssembly(typeof(DependencyInjection).Assembly));

    services.AddValidatorsFromAssembly(typeof(DependencyInjection).Assembly);

    // No more service registrations needed!
    // services.AddScoped<IDepartmentService, DepartmentService>();  ← GONE

    return services;
}

RegisterServicesFromAssembly scans for all IRequestHandler implementations — just like AddValidatorsFromAssembly scans for validators.

2

Create Your First Query

Create a folder: Features/Departments/Queries/GetAllDepartments/

GetAllDepartmentsQuery.cs:

using MediatR;

public class GetAllDepartmentsQuery : IRequest<PagedResponse<DepartmentResponse>>
{
    public int PageNumber { get; set; } = 1;
    public int PageSize { get; set; } = 10;
    public string? Search { get; set; }
    public bool? IsActive { get; set; }
    public string? SortBy { get; set; }
    public bool SortDescending { get; set; }
}

GetAllDepartmentsHandler.cs:

public class GetAllDepartmentsHandler
    : IRequestHandler<GetAllDepartmentsQuery, PagedResponse<DepartmentResponse>>
{
    private readonly IUnitOfWork _unitOfWork;

    public GetAllDepartmentsHandler(IUnitOfWork unitOfWork)
    {
        _unitOfWork = unitOfWork;
    }

    public async Task<PagedResponse<DepartmentResponse>> Handle(
        GetAllDepartmentsQuery request,
        CancellationToken cancellationToken)
    {
        var filters = new List<Expression<Func<Department, bool>>>();

        filters.Add(d => d.IsActive == (request.IsActive ?? true));

        if (!string.IsNullOrWhiteSpace(request.Search))
        {
            var search = request.Search.ToLower();
            filters.Add(d => d.Name.ToLower().Contains(search)
                           || d.Code.ToLower().Contains(search));
        }

        var pagedRequest = new PagedRequest
        {
            PageNumber = request.PageNumber,
            PageSize = request.PageSize,
            SortBy = request.SortBy,
            SortDescending = request.SortDescending
        };

        var paged = await _unitOfWork.Departments.GetPagedAsync(pagedRequest, filters);

        return new PagedResponse<DepartmentResponse>
        {
            Items = paged.Items.Select(d => d.ToResponse()).ToList(),
            PageNumber = paged.PageNumber,
            PageSize = paged.PageSize,
            TotalCount = paged.TotalCount
        };
    }
}

5. Pipeline Behaviors — MediatR's Middleware

What Are They?

Pipeline Behaviors are to MediatR what Middleware is to the HTTP pipeline. They wrap every request that passes through MediatR.

HTTP Middleware

HTTP Request
  → ExceptionMiddleware
    → AuthMiddleware
      → Controller
    ← AuthMiddleware
  ← ExceptionMiddleware
HTTP Response

MediatR Behaviors

_mediator.Send(request)
  → LoggingBehavior
    → ValidationBehavior
      → Handler
    ← ValidationBehavior
  ← LoggingBehavior
return result

Validation Behavior — Automatic Validation

Remember how every service method starts with this?

// You copy-paste this in EVERY Create/Update method:
var validationResult = await _validator.ValidateAsync(request);
if (!validationResult.IsValid)
    throw new ValidationException(validationResult.ToErrorDictionary());

With a ValidationBehavior, you write it once and it runs automatically for every request that has a matching validator:

using FluentValidation;
using MediatR;

public class ValidationBehavior<TRequest, TResponse>
    : IPipelineBehavior<TRequest, TResponse>
    where TRequest : notnull
{
    private readonly IEnumerable<IValidator<TRequest>> _validators;

    public ValidationBehavior(IEnumerable<IValidator<TRequest>> validators)
    {
        _validators = validators;
    }

    public async Task<TResponse> Handle(
        TRequest request,
        RequestHandlerDelegate<TResponse> next,   // ← like _next(context) in middleware
        CancellationToken cancellationToken)
    {
        if (!_validators.Any())
            return await next();   // No validator registered for this type → skip

        var context = new ValidationContext<TRequest>(request);

        var failures = _validators
            .Select(v => v.Validate(context))
            .SelectMany(result => result.Errors)
            .Where(f => f != null)
            .ToList();

        if (failures.Any())
        {
            var errors = failures
                .GroupBy(f => f.PropertyName)
                .ToDictionary(
                    g => g.Key,
                    g => g.Select(f => f.ErrorMessage).ToArray());

            throw new ValidationException(errors);
        }

        return await next();   // Validation passed → call the actual handler
    }
}

How this works

  • MediatR calls this behavior before every handler
  • DI injects IEnumerable<IValidator<TRequest>> — if there's a CreateDepartmentValidator registered and the request is CreateDepartmentCommand, it gets injected
  • If there's no validator for this request type, the IEnumerable is empty → skips validation
  • next() is like await _next(context) in HTTP middleware — it calls the next behavior or the handler
  • If validation fails, it throws before the handler runs — same as your current service code, but without any handler needing to know about validation

Logging Behavior — Automatic Request Logging

public class LoggingBehavior<TRequest, TResponse>
    : IPipelineBehavior<TRequest, TResponse>
    where TRequest : notnull
{
    private readonly ILogger<LoggingBehavior<TRequest, TResponse>> _logger;

    public LoggingBehavior(ILogger<LoggingBehavior<TRequest, TResponse>> logger)
    {
        _logger = logger;
    }

    public async Task<TResponse> Handle(
        TRequest request,
        RequestHandlerDelegate<TResponse> next,
        CancellationToken cancellationToken)
    {
        var requestName = typeof(TRequest).Name;

        _logger.LogInformation("Handling {RequestName}", requestName);

        var stopwatch = Stopwatch.StartNew();
        var response = await next();
        stopwatch.Stop();

        _logger.LogInformation("Handled {RequestName} in {ElapsedMs}ms",
            requestName, stopwatch.ElapsedMilliseconds);

        return response;
    }
}

Now every request is automatically logged with timing:

// Output:
// [INF] Handling CreateDepartmentCommand
// [INF] Handled CreateDepartmentCommand in 42ms
// [INF] Handling GetAllDepartmentsQuery
// [INF] Handled GetAllDepartmentsQuery in 8ms

Registering Behaviors

services.AddMediatR(cfg =>
{
    cfg.RegisterServicesFromAssembly(typeof(DependencyInjection).Assembly);

    // Pipeline behaviors — order matters!
    cfg.AddBehavior(typeof(LoggingBehavior<,>));
    cfg.AddBehavior(typeof(ValidationBehavior<,>));
});

Execution Order

Behaviors execute in the order they're registered — outermost first:

Request arrives → LoggingBehavior (logs "Handling...") → ValidationBehavior (validates, throws if invalid) → Handler (does the actual work) ← ValidationBehavior ← LoggingBehavior (logs "Handled in Xms") Response returned

Why Logging before Validation?

If validation fails, the LoggingBehavior will still log the request name — so you know someone tried to create a department with invalid data. If Logging was after Validation, you'd never see failed attempts in your logs.

6. Advanced Patterns

Notifications — One Event, Many Handlers

IRequest is one-to-one: one request, one handler. INotification is one-to-many: one event, multiple handlers react to it.

// The event
public class DepartmentCreatedNotification : INotification
{
    public int DepartmentId { get; set; }
    public string Name { get; set; }
}

// Handler 1: Invalidate cache
public class InvalidateCacheHandler
    : INotificationHandler<DepartmentCreatedNotification>
{
    public Task Handle(DepartmentCreatedNotification notification, CancellationToken ct)
    {
        // Clear department cache
        return Task.CompletedTask;
    }
}

// Handler 2: Send email notification
public class SendEmailHandler
    : INotificationHandler<DepartmentCreatedNotification>
{
    public Task Handle(DepartmentCreatedNotification notification, CancellationToken ct)
    {
        // Send email to admin about new department
        return Task.CompletedTask;
    }
}

// Publishing (in the CreateDepartmentHandler):
await _mediator.Publish(new DepartmentCreatedNotification
{
    DepartmentId = department.Id,
    Name = department.Name
});

Send vs Publish

_mediator.Send() _mediator.Publish()
Interface IRequest<T> INotification
Handlers Exactly 1 0 or more
Returns A result Nothing (void)
Use for Commands & Queries Domain Events (side effects)

Commands Without Return Value

Delete doesn't return anything. Use IRequest (without generic parameter) or IRequest<Unit>:

public class DeleteDepartmentCommand : IRequest
{
    public int Id { get; set; }
}

public class DeleteDepartmentHandler : IRequestHandler<DeleteDepartmentCommand>
{
    public async Task Handle(
        DeleteDepartmentCommand request,
        CancellationToken cancellationToken)
    {
        var dept = await _unitOfWork.Departments.FindAsync(d => d.Id == request.Id && d.IsActive);
        if (dept is null) throw new NotFoundException("Department", request.Id);

        dept.IsActive = false;
        dept.UpdatedAt = DateTime.UtcNow;
        _unitOfWork.Departments.Update(dept);
        await _unitOfWork.SaveChangesAsync();
    }
}

CancellationToken

Every handler receives a CancellationToken. This lets the operation be cancelled if the client disconnects:

public async Task<PagedResponse<DepartmentResponse>> Handle(
    GetAllDepartmentsQuery request,
    CancellationToken cancellationToken)  ← MediatR passes this
{
    // Pass it to async EF Core calls:
    var count = await query.CountAsync(cancellationToken);
    var items = await query.ToListAsync(cancellationToken);
    // If the client disconnects, these calls are cancelled → no wasted DB work
}

8. When to Use What

Use Simple Service When

  • Small project, few endpoints (5-10)
  • Team of 1-2 developers
  • Operations are basic CRUD
  • No need for cross-cutting pipeline
  • Rapid prototyping

Use CQRS + MediatR When

  • Medium-large project, many endpoints
  • Multiple developers (less merge conflicts)
  • Complex business logic per operation
  • Reads and writes need different optimization
  • You want automatic validation/logging pipeline
  • You need domain events (notifications)

9. Interview Questions

Q: What is CQRS and when would you use it?

CQRS separates read operations (queries) from write operations (commands) into different models. Each operation gets its own class and handler, following Single Responsibility Principle. I'd use it when the application has complex business logic, different optimization needs for reads vs writes, or when working on a team to reduce merge conflicts. For simple CRUD apps, a service layer is sufficient.

Q: What is MediatR and how does it work?

MediatR is an in-process mediator library that decouples the sender of a request from its handler. The controller sends a request object via _mediator.Send(). MediatR scans the DI container for a class implementing IRequestHandler<TRequest, TResponse> matching that request type, and calls its Handle method. It's registered via assembly scanning, similar to how FluentValidation auto-registers validators.

Q: What are Pipeline Behaviors?

Pipeline Behaviors are MediatR's equivalent of HTTP middleware. They implement IPipelineBehavior<TRequest, TResponse> and wrap every request. The next() delegate calls the next behavior or the handler — exactly like await _next(context) in middleware. Common uses: automatic validation (run FluentValidation before every handler), logging with timing, caching, and transaction management.

Q: What's the difference between Send and Publish in MediatR?

Send() dispatches an IRequest<T> to exactly one handler and returns a result. Used for commands and queries. Publish() dispatches an INotification to zero or more handlers with no return value. Used for domain events — e.g., after creating a department, publish a notification that triggers cache invalidation AND email sending independently.

Q: How do Commands differ from Queries in CQRS?

Commands change state (Create, Update, Delete) — they have side effects and usually need validation. Queries read state (GetAll, GetById) — they're idempotent and don't modify data. Separating them lets you optimize each independently: queries can use caching, read replicas, and projections, while commands can use transactions, validation, and domain events.

Q: Can you implement CQRS without MediatR?

Yes. CQRS is a pattern, MediatR is a library. You could have separate ICommandHandler<T> and IQueryHandler<T, TResult> interfaces with manual DI registration. MediatR just provides a convenient dispatcher, pipeline behaviors, and assembly scanning. In fact, some teams prefer their own lightweight mediator to avoid the MediatR dependency.

Q: What are the downsides of CQRS?

More files (each operation = 2-3 files vs 1 method in a service). Can feel like over-engineering for simple CRUD. Debugging is harder — you're jumping through mediator dispatch instead of direct method calls. The indirection makes the flow less obvious to junior developers. Also, if your reads and writes are similar (basic CRUD), the separation adds complexity without real benefit.

Q: How does the ValidationBehavior know which validator to use?

It injects IEnumerable<IValidator<TRequest>>. When MediatR processes a CreateDepartmentCommand, the behavior's generic type resolves to IValidator<CreateDepartmentCommand>. If a CreateDepartmentValidator : AbstractValidator<CreateDepartmentCommand> is registered in DI, it gets injected. If no validator exists for that type, the collection is empty and validation is skipped.

Q: Where does validation happen in a CQRS architecture?

In a Pipeline Behavior, not in the handler. The ValidationBehavior runs before the handler, checking if a FluentValidation validator exists for the request type. This removes all validation boilerplate from handlers — they can assume the input is already valid. It's the same concept as having validation middleware in the HTTP pipeline, but at the MediatR level.

Q: How do you handle cross-cutting concerns in CQRS?

Through MediatR Pipeline Behaviors. They're composable — you can chain LoggingBehavior → ValidationBehavior → CachingBehavior → Handler. Each behavior calls next() to pass to the next one, like middleware. This keeps handlers focused on business logic only, while cross-cutting concerns (logging, validation, caching, transactions) are handled generically and applied to all requests.

10. Cheat Sheet

Concept Interface Purpose
Query IRequest<TResponse> Read operation — carries filter/pagination params
Command IRequest<TResponse> or IRequest Write operation — carries data to create/update
Handler IRequestHandler<TRequest, TResponse> Does the actual work — one per command/query
Notification INotification Domain event — one-to-many (multiple handlers react)
Notification Handler INotificationHandler<T> Reacts to a notification (cache clear, email, log)
Behavior IPipelineBehavior<TRequest, TResponse> Middleware — wraps every request (validation, logging)
Dispatcher IMediator Sends requests to handlers — injected in controllers

Quick Reference — Creating a New Feature

// 1. Create the Command/Query
public class DoSomethingCommand : IRequest<SomeResponse>
{
    // properties = input data
}

// 2. Create the Handler
public class DoSomethingHandler : IRequestHandler<DoSomethingCommand, SomeResponse>
{
    public async Task<SomeResponse> Handle(
        DoSomethingCommand request,
        CancellationToken ct)
    {
        // do the work
    }
}

// 3. (Optional) Create a Validator
public class DoSomethingValidator : AbstractValidator<DoSomethingCommand>
{
    public DoSomethingValidator()
    {
        RuleFor(x => x.Name).NotEmpty();
    }
}

// 4. Call from Controller
var result = await _mediator.Send(new DoSomethingCommand { Name = "test" });

// That's it. MediatR auto-discovers the handler.
// ValidationBehavior auto-validates if a validator exists.
// LoggingBehavior auto-logs timing.
// No service interface, no manual DI registration.
