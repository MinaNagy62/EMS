M5 Sprint 1 — MediatR & CQRS

Everything explained step by step, in simple words.

1. What Problem Are We Solving?

Before (Old Way — Service Pattern)

The controller calls the service directly. The service does everything: validation, business logic, database calls, caching.

Controller ──→ DepartmentService ──→ Repository ──→ Database The service has ALL methods: - GetAllDepartmentsAsync() ← read - GetDepartmentByIdAsync() ← read - CreateDepartmentAsync() ← write - UpdateDepartmentAsync() ← write - DeleteDepartmentAsync() ← write

The problem: As the project grows, the service becomes a giant file with 500+ lines. Reads and writes are mixed together. Every method has different dependencies. Hard to test, hard to maintain.

After (New Way — CQRS with MediatR)

CQRS = Command Query Responsibility Segregation. Big name, simple idea:

Queries = reading data (GET). Each query is its own class + handler.

Commands = changing data (POST/PUT/DELETE). Each command is its own class + handler.

They are separated. Each operation lives in its own file with only the dependencies it needs.

Controller ──→ IMediator ──→ finds the right Handler ──→ Repository GET /department → GetAllDepartmentsQuery → GetAllDepartmentsHandler GET /department/5 → GetDepartmentByIdQuery → GetDepartmentByIdHandler POST /department → CreateDepartmentCommand → CreateDepartmentHandler (Sprint 2) PUT /department/5 → UpdateDepartmentCommand → UpdateDepartmentHandler (Sprint 2) DELETE /department → DeleteDepartmentCommand → DeleteDepartmentHandler (Sprint 2)

What is MediatR?

MediatR is a library that acts as a middleman (mediator). The controller doesn't know which handler exists. It just says "here's a request, find someone who can handle it."

Controller: "Hey MediatR, here's a GetAllDepartmentsQuery" MediatR: "Let me find who handles that..." MediatR: "Found it! GetAllDepartmentsHandler, here you go." Handler: *does the work, returns the result* MediatR: "Controller, here's your result."

The controller never imports or knows about the handler. MediatR connects them automatically based on the types.

3. Step-by-Step: What Each File Does

1Install MediatR Package

dotnet add package MediatR

This gives us the IMediator, IRequest<T>, IRequestHandler<TRequest, TResponse>, and IPipelineBehavior interfaces.

2Register MediatR in DependencyInjection.cs

EMS_Application/DependencyInjection.cs

services.AddMediatR(cfg =>
    cfg.RegisterServicesFromAssembly(Assembly.GetExecutingAssembly()));

services.AddTransient(typeof(IPipelineBehavior<,>), typeof(ValidationBehavior<,>));

RegisterServicesFromAssembly tells MediatR: "Scan this project. Find every class that implements IRequestHandler and register it automatically." You never manually register handlers — MediatR discovers them.

AddTransient(typeof(IPipelineBehavior<,>), typeof(ValidationBehavior<,>)) tells MediatR: "Before any handler runs, run the ValidationBehavior first." It's like middleware but for MediatR.

3GetAllDepartmentsQuery — The Request

Features/Departments/Queries/GetAllDepartments/GetAllDepartmentsQuery.cs

public class GetAllDepartmentsQuery : PagedRequest, IRequest<PagedResponse<DepartmentResponse>>
{
    public string? Search { get; set; }
    public bool? IsActive { get; set; }
}

This is just a data class. It says:

  • I inherit from PagedRequest → so I have PageNumber, PageSize, SortBy, SortDescending
  • I add Search and IsActive → same as the old DepartmentQueryRequest
  • IRequest<PagedResponse<DepartmentResponse>> → "I'm a request, and my answer will be a PagedResponse of DepartmentResponse"

Why not reuse DepartmentQueryRequest? Because in CQRS, the query IS the request. It implements IRequest<T> which MediatR needs to route it to the right handler. DepartmentQueryRequest was just a DTO — it didn't implement IRequest.

5GetDepartmentByIdQuery + Handler

Features/Departments/Queries/GetDepartmentById/

// Query — just an Id
public class GetDepartmentByIdQuery : IRequest<DepartmentResponse>
{
    public int Id { get; set; }
}

// Handler — find it or throw
public class GetDepartmentByIdHandler
    : IRequestHandler<GetDepartmentByIdQuery, DepartmentResponse>
{
    public async Task<DepartmentResponse> Handle(...)
    {
        var department = await _unitOfWork.Departments.FindAsync(
            d => d.Id == request.Id && d.IsActive);

        if (department is null)
            throw new NotFoundException("Department", request.Id);

        return department.ToResponse();
    }
}

Same pattern. Query = what I want. Handler = how to get it. This handler only needs IUnitOfWork — nothing else.

6ValidationBehavior — Auto Validation

Behaviors/ValidationBehavior.cs

This is a MediatR pipeline behavior. Think of it like middleware, but for MediatR requests instead of HTTP requests:

HTTP Request → Middleware Pipeline → Controller ↓ MediatR Request → ValidationBehavior → Handler
public class ValidationBehavior<TRequest, TResponse>
    : IPipelineBehavior<TRequest, TResponse>
{
    private readonly IEnumerable<IValidator<TRequest>> _validators;

    public async Task<TResponse> Handle(
        TRequest request,
        RequestHandlerDelegate<TResponse> next,
        CancellationToken cancellationToken)
    {
        // 1. No validators registered for this request? Skip.
        if (!_validators.Any())
            return await next();

        // 2. Run all validators
        var validationResults = await Task.WhenAll(
            _validators.Select(v => v.ValidateAsync(context)));

        // 3. Collect errors
        var errors = validationResults
            .SelectMany(r => r.Errors)
            .Where(f => f is not null)
            .ToList();

        // 4. Errors found? Throw. Handler never runs.
        if (errors.Count > 0)
            throw new ValidationException(errorDictionary);

        // 5. No errors? Call the actual handler.
        return await next();
    }
}

How it works step by step:

1. MediatR receives a request (e.g., GetAllDepartmentsQuery)

2. Before calling the handler, it runs ValidationBehavior

3. ValidationBehavior asks DI: "Are there any IValidator<GetAllDepartmentsQuery> registered?"

4. If yes → run them. If validation fails → throw ValidationException. Handler never executes.

5. If no validators exist OR validation passes → next() calls the actual handler.

Why is this better? In the old service, every method had to manually call the validator:

// OLD — manual validation in every method
var validationResult = await _createValidator.ValidateAsync(request);
if (!validationResult.IsValid)
    throw new ValidationException(validationResult.ToErrorDictionary());

// NEW — automatic. Just create a validator class and it runs automatically.
// The handler doesn't even know validation exists.

IEnumerable<IValidator<TRequest>> — DI injects ALL validators for this request type. If there are none, the list is empty (not null), so _validators.Any() returns false and we skip validation.

4. The Full Flow — How a Request Travels

GET /api/department?search=HR&pageSize=5

1. Client sends GET request ↓ 2. ASP.NET model binding creates GetAllDepartmentsQuery { Search = "HR", PageSize = 5, PageNumber = 1 (default) } ↓ 3. Controller calls _mediator.Send(query) ↓ 4. MediatR looks at the type: GetAllDepartmentsQuery It knows GetAllDepartmentsHandler handles this type ↓ 5. Before the handler runs → ValidationBehavior executes → Checks: any IValidator<GetAllDepartmentsQuery> registered? → No validators → skips validation → calls next() ↓ 6. GetAllDepartmentsHandler.Handle() runs → Checks cache → miss → Builds filters (IsActive=true, Search contains "HR") → Queries database with pagination → Stores result in cache → Returns PagedResponse<DepartmentResponse> ↓ 7. MediatR returns the result to the controller ↓ 8. Controller wraps in ApiResponse and returns 200 OK

GET /api/department/5

1. Controller creates new GetDepartmentByIdQuery { Id = 5 } ↓ 2. _mediator.Send(query) ↓ 3. ValidationBehavior → no validators → skip → next() ↓ 4. GetDepartmentByIdHandler.Handle() → FindAsync(d => d.Id == 5 && d.IsActive) → Found? Return DepartmentResponse → Not found? Throw NotFoundException ↓ 5. Controller wraps in ApiResponse and returns 200 OK

5. How MediatR Finds the Right Handler

This is the "magic" part. Here's how it actually works:

At startup:

services.AddMediatR(cfg =>
    cfg.RegisterServicesFromAssembly(Assembly.GetExecutingAssembly()));

MediatR scans every class in the assembly. It finds:

GetAllDepartmentsHandler : IRequestHandler<GetAllDepartmentsQuery, PagedResponse<...>>
GetDepartmentByIdHandler : IRequestHandler<GetDepartmentByIdQuery, DepartmentResponse>

It registers them in DI automatically:

// MediatR does this behind the scenes:
services.AddTransient<IRequestHandler<GetAllDepartmentsQuery, PagedResponse<...>>,
                       GetAllDepartmentsHandler>();
services.AddTransient<IRequestHandler<GetDepartmentByIdQuery, DepartmentResponse>,
                       GetDepartmentByIdHandler>();

At runtime:

_mediator.Send(new GetAllDepartmentsQuery { ... });

MediatR sees the type is GetAllDepartmentsQuery. It asks DI:

"Give me the IRequestHandler<GetAllDepartmentsQuery, PagedResponse<...>>"

DI returns GetAllDepartmentsHandler. MediatR calls its Handle() method.

It's just dependency injection + generics. No reflection at runtime. No magic.

6. ValidationBehavior — The Pipeline Concept

MediatR has a pipeline — behaviors that run before/after every handler, like layers of an onion:

Request comes in ↓ ┌─────────────────────────────┐ │ ValidationBehavior │ ← runs FIRST │ (checks for validation │ │ errors before handler) │ │ ↓ │ │ ┌────────────────────┐ │ │ │ Actual Handler │ │ ← runs if validation passes │ │ (does the work) │ │ │ └────────────────────┘ │ │ ↓ │ │ Result goes back up │ └─────────────────────────────┘ ↓ Response goes out

You can add more behaviors later:

Request → LoggingBehavior → ValidationBehavior → CachingBehavior → Handler → Response

Each behavior decides: do I continue to the next one (await next()) or do I stop here (throw exception)?

7. Why CQRS? The Benefits

Old Service CQRS with MediatR
One big service file with all methods Each operation is its own file
All dependencies injected even if not needed Each handler only injects what it needs
Manual validation in every method Automatic validation via pipeline behavior
Controller knows about the service Controller only knows IMediator — fully decoupled
Hard to add cross-cutting concerns Just add another pipeline behavior (logging, caching, etc.)
Reads and writes mixed together Queries/ and Commands/ are separate folders

8. The Key Interfaces — Cheat Sheet

Interface What It Does Who Implements It
IRequest<T> Marks a class as a MediatR request that returns T Query and Command classes
IRequestHandler<TRequest, TResponse> Handles a specific request type Handler classes
IMediator The middleman — routes requests to handlers Provided by MediatR (you inject it)
IPipelineBehavior<TRequest, TResponse> Runs before/after every handler (like middleware) ValidationBehavior, LoggingBehavior, etc.
